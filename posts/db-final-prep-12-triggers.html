12. Triggers

Oct 25, 2026 · DB-FINAL-PREP · Databases · Author: Algo-holics · Source: https://t.me/kbtukbtu/372/640

Description

A PostgreSQL trigger is a function invoked automatically whenever an event associated with a table occurs. Events: INSERT, UPDATE, DELETE or TRUNCATE. A trigger is a special user-defined function bound to a table: you first define a trigger function, then bind it to a table with CREATE TRIGGER.

Trigger Types

  • Row-level triggers: fire once for each row affected (FOR EACH ROW).
  • Statement-level triggers: fire once per statement, regardless of how many rows are affected (FOR EACH STATEMENT).

They differ in how many times the trigger is invoked and at what time (BEFORE or AFTER the event).

When to Use Triggers

Triggers are useful when many applications access the database and you want cross-cutting behaviour to run automatically inside the database whenever data changes. Example: keep a history/audit of data changes without every application having to implement logic for each INSERT or UPDATE.

PostgreSQL vs. SQL-Standard Triggers

  • PostgreSQL fires triggers for the TRUNCATE event.
  • PostgreSQL allows statement-level triggers on views.
  • PostgreSQL requires the action to be a user-defined function, while the SQL standard allows any SQL command.

Creating a Trigger

Step 1: Create the trigger function

CREATE FUNCTION trigger_function()
RETURNS TRIGGER
LANGUAGE PLPGSQL
AS $$
BEGIN
    -- trigger logic
    RETURN NEW;
END;
$$;

Inside a row-level trigger function, NEW is the new row (INSERT/UPDATE) and OLD is the previous row (UPDATE/DELETE).

Step 2: Bind it with CREATE TRIGGER

CREATE TRIGGER trigger_name
    {BEFORE | AFTER} {event}
    ON table_name
    [FOR [EACH] {ROW | STATEMENT}]
    EXECUTE PROCEDURE trigger_function();   -- or EXECUTE FUNCTION

Complete Example: Auditing Last-Name Changes

DROP TABLE IF EXISTS employees;
CREATE TABLE employees (
    id         INT GENERATED ALWAYS AS IDENTITY,
    first_name VARCHAR(40) NOT NULL,
    last_name  VARCHAR(40) NOT NULL,
    PRIMARY KEY (id)
);

CREATE TABLE employee_audits (
    id          INT GENERATED ALWAYS AS IDENTITY,
    employee_id INT NOT NULL,
    last_name   VARCHAR(40) NOT NULL,
    changed_on  TIMESTAMP(6) NOT NULL
);

-- 1) Trigger function
CREATE OR REPLACE FUNCTION log_last_name_changes()
RETURNS TRIGGER
LANGUAGE PLPGSQL
AS $$
BEGIN
    IF NEW.last_name <> OLD.last_name THEN
        INSERT INTO employee_audits (employee_id, last_name, changed_on)
        VALUES (OLD.id, OLD.last_name, now());
    END IF;
    RETURN NEW;
END;
$$;

-- 2) Trigger
CREATE TRIGGER last_name_changes
    BEFORE UPDATE
    ON employees
    FOR EACH ROW
    EXECUTE PROCEDURE log_last_name_changes();

-- Test
INSERT INTO employees (first_name, last_name) VALUES ('John', 'Doe'), ('Lily', 'Bush');
UPDATE employees SET last_name = 'Brown' WHERE id = 2;
SELECT * FROM employee_audits;   -- shows Lily's old last name 'Bush'

Managing Triggers

-- Remove a trigger
DROP TRIGGER [IF EXISTS] trigger_name
ON table_name [CASCADE | RESTRICT];

DROP TRIGGER last_name_changes ON employees;

-- Rename a trigger
ALTER TRIGGER trigger_name
ON table_name
RENAME TO new_trigger_name;

ALTER TRIGGER before_update_salary ON employees RENAME TO salary_before_update;

Conclusion

Triggers automate reactions to data changes (auditing, validation, derived data) directly inside the database, independent of which application changes the data. Use them deliberately, since hidden automatic behaviour can make debugging harder.
