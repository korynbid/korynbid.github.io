16. Fallacies and Pitfalls

Oct 25, 2026 · COMPARCH · Computer Architecture · Author: Algo-holics · Source: https://t.me/kbtukbtu/583

Description

A fallacy is a widely believed idea that is false; a pitfall is an easily made mistake. Recognizing them is a core skill when judging architecture claims.

TypeStatementWhy it is wrong / the correct view
Fallacy"A higher clock rate means a faster computer."Performance = IC × CPI × T. Clock alone ignores CPI, instruction count, memory and power.
PitfallUsing MIPS to compare machinesIgnores what each instruction does; use execution time on real workloads.
PitfallIgnoring Amdahl's LawSpeeding up a small fraction gives a small total gain; serial fractions cap parallel speedup.
Fallacy"Adding cores gives linear speedup."Synchronization, bandwidth and serial code limit scaling.
Fallacy"Peak performance is what programs get."Real code reaches a fraction of peak (memory-bound, imbalance). Use the roofline.
Fallacy"A performance improvement also improves energy efficiency."Faster techniques (e.g. wider speculation) can cost more energy per task.
Fallacy"Bigger caches/more associativity are always better."They raise hit time, energy and area; there is an optimum.
PitfallForgetting false sharing and data alignmentSilent slowdowns on multicore and SIMD code.
Fallacy"Disks fail at the rate implied by the MTTF."Field failure rates are often higher than the datasheet suggests.
Fallacy"ARM and x86 both use weak memory models."x86 is TSO (strong); ARM/RISC-V are relaxed.
PitfallTreating speculation as freeWrong paths waste energy and can leak data (Spectre).
PitfallIgnoring tail latency in large servicesFan-out makes rare slow events common (Topic 14).
Fallacy"One big server can handle a WSC-scale job."Network latency, memory and failure rates force scale-out designs.
PitfallUnder-provisioned cooling and power for new serversCapacity, not just hardware, limits a data center.
Fallacy"Benchmarks stay valid forever."Workloads change; benchmarks must be updated and representative.
Fallacy"Domain-specific chips will replace CPUs."They accelerate fixed kernels; general-purpose CPUs still run everything else.
PitfallAssuming VLIW compilers can always find enough parallelismUnpredictable cache misses and branches defeat static scheduling (Itanium).

Key Formulas

None new. Re-check the formulas in Topics 1, 4, 6 and 13 against each statement above.

Steps

To test a claim: (1) identify the metric (time, energy, throughput), (2) write the relevant equation, (3) look for the hidden variable the claim ignores (CPI, serial fraction, miss penalty, power), (4) answer with numbers if possible.

Worked Example

Claim: "Machine A runs at 4 GHz, machine B at 3 GHz, so A is faster." Same program: A has CPI 2.4 → time per instruction 2.4 / 4 = 0.60 ns; B has CPI 1.5 → 1.5 / 3 = 0.50 ns. B is faster (1.2×) despite the lower clock.

Claim: "Doubling cores doubles speed." For f = 0.9: 4 cores → 1/(0.1 + 0.225) = 3.08; 8 cores → 1/(0.1 + 0.1125) = 4.71, not 6.15 or 8.

Python / Assembly

def time_per_instr_ns(cpi, ghz):
    return cpi / ghz

print(time_per_instr_ns(2.4, 4.0), time_per_instr_ns(1.5, 3.0))    # 0.6 0.5
amdahl = lambda f, n: 1 / ((1 - f) + f / n)
print(round(amdahl(0.9, 4), 2), round(amdahl(0.9, 8), 2))         # 3.08 4.71

Notes

  • Treat each claim as "True/False: explain"; always give the reason, not only the verdict.
  • WSC fallacies: expecting high single-server performance without counting network delay; pitfalls: scaling difficulty and excess power use, such as insufficient cooling.
